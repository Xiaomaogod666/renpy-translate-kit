# 不带 game/ 前缀的 RPA 条目按 game/ 下的路径处理

有些游戏打 `.rpa` 包时不给条目带 `game/` 前缀（条目形如 `content/xxx.rpyc`、`script.rpyc`），
标准打包则是 `game/content/xxx.rpyc`。引擎运行时对压缩包内路径按搜索路径
（即 `game/`）解析，两种打包都能正常游玩；但 1.0.0 的解包把条目路径直接拼到游戏根目录，
无前缀的脚本就被散落到了根目录 —— 引擎不读那里，导出流程也看不见那里，
于是 `game/` 下始终没有明文 `.rpy`，导出只能捞到引擎自带的 common 文本
（`translate_list_files()` 只认磁盘上 `game/` 下的 `.rpy`）。

因此解包、缺文件判定统一加一条归一化规则：**条目不以 `game/` 开头的，一律视作
`game/` 下的相对路径**（`rpa_entry_game_rel`）。这与引擎的加载语义完全一致，
对标准打包的游戏零影响。

## 考虑过的其它做法

- **把无前缀条目解到游戏根目录并让引擎去根目录找**：要改引擎的搜索路径，
  动的是引擎和游戏行为，风险与收益完全不成比例。
- **只修导出端，让导出去根目录找脚本**：导出之所以只认 `game/` 下的 `.rpy`，
  是引擎 `translate_list_files()` 的行为，外壳绕不开；而且脚本散在根目录本身就错，
  游戏自己也可能因为更新/校验产生混乱。
- **检测到根目录散落脚本时提示用户手动清理**：多一步人工操作，用户无从判断
  哪些能删。改成自动清理更符合"拖进来就完事"的定位。

## 后果

- 无前缀打包的游戏（如 Deviant Anomalies X）从"只能导出引擎公共文本"变为正常全量导出。
- 解包时顺手清理旧版本错放到根目录的脚本副本：只删与包内内容逐字节相同的副本，
  内容不同的文件保留（可能另有用处），清空的目录一并回收。
- 解包补进新脚本后，若该语言已导入过，会自动重新读取一遍语言 —— 文本清单变大了，
  旧的导入是残缺的。重新导入会清掉该语言的旧进度再重建（已翻译内容仍保留在
  工作区 `*_translated.json` 中，可对照重贴）；这是唯一会"动进度"的场景，
  且只发生在确实解出了新文件的时候。
