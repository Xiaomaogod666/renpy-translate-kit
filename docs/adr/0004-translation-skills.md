# 0004. 翻译质量靠外装技能补齐, 不再只靠自写提示词

日期: 2026-09-28
状态: 已采用

## 背景

第一轮全量翻译 (约 9800 条) 完成后, 用户判断「机翻味太重」。

对 9000 条已出译文做了量化诊断, 结论是**译文本身没有错译**: 语义准确、术语一致、
变量与标签保留完好、长度收敛正常 (中文/英文长度比中位 0.333)。问题全部出在**句式层面**:

- 冠词残留「一个/这个/是个」171 处 (`The kidnapping or the fact that a guy...` →
  「绑架本身，还是**一个**浑身湿透…的家伙」)
- 从句名词化 `That's what pushes me.` → 「这才是推着我往前走的**东西**」
- 连接词硬搬 `so` → 「所以」、`which means` → 「也就是说」
- 判断句倒装 `She's the one who wouldn't let me go` → 「不放我走的，是她」
- 「的」字堆叠、被动滥用、书面词 (`本职工作`/`成为`/`极其`) 出现在口语对白里
- 短应答通篇一个译法: `I see.` 全译「我明白了」、句尾 `yeah` 全译「是的」

这些是**翻译腔 (translationese)**, 是英译汉的通用病症, 属于方法论问题而非语料问题。
原提示词里只有「按语境翻」「语气跟着原作走」这类原则, 缺少「哪些句式是错的」的可操作清单。

## 考虑过的其它做法

1. **继续自己扩写提示词**: 把诊断出的病症逐条写进 `翻译提示词.md`。
   成本最低, 但等于重新发明一遍英译汉方法论 —— 现成的成熟方法论已经存在且质量更高
   (如「词性转换」「拆句合句」「归化档位」这些系统性手法, 自己写不出这个完整度)。
2. **找一个端到端自动翻译的插件装上**: 先扫描了两个已知市场
   (`zcode-plugins-official` 40 插件 + `claude-plugins-official` 291 插件),
   关键词 translat/localiz/i18n/翻译 **零命中**; 另查 `anthropics/skills` (19) 与
   `obra/superpowers` (15) 也零翻译技能。**业界没有官方翻译技能可装**。
3. **装 GitHub 上的第三方翻译技能** (采用)。

## 采用

从 GitHub 挑两个 MIT 许可、维护中的技能, 手工装进 ZCode 用户技能目录
`%USERPROFILE%\.zcode\skills\`:

- **`en-zh-translation-polish`** (HoraceLuBFA, 112★, MIT) —— 英译汉润色方法论。
  七阶段流程: 文本分析定归化档位 → 理解脱壳 → 意合优先初译 → 润色诊断 →
  音韵节奏 → 准确性质检 → 标点归一。核心资产是 `reference/translationese-symptoms.md`
  的**九类翻译腔病症表**, 正好覆盖上面诊断出的每一类。方法论蒸馏自叶子南《高级英汉翻译理论与实践》。
- **`renpy-translation`** (Waiyakorn1879/for-the-plot, MIT) —— Ren'Py 游戏本地化管线。
  角色语域模型 (同一角色对不同人用不同自称)、token 多重集校验、
  翻译记忆、断点续跑。实战验证过 Being a DIK 泰语 36k 串。

选择依据: 两者都是 MIT 且维护中; 前者补「怎么写得不像机翻」, 后者补「游戏对白的工程约束」。
另有三个候选因**无 LICENSE** 放弃安装 (仅作参考): `Ly1NG114/renpy-localization-skill`
(亲属称谓方向性讲得最透, 但不合规不能 vendor)、`Cuimao777/cuimao-translator` (485★)、
`rookie-ricardo/erduo-skills`。`JimLiu/baoyu-skills/baoyu-translate` 装量最高 (26k★) 但
词表只有 ~20 个技术词, **无汉语翻译腔方法论**, 与本需求不匹配。

装法是 tarball 解包后逐文件复制 + md5 校验, 不改动 frontmatter 的 `name`/`description`;
只给缺触发语的 `en-zh-translation-polish` 补了一行 `when_to_use`
(该技能原本只有 description, 按 skill 加载规则 description 会被截断到 ~250 字符,
补 `when_to_use` 能让「怀疑译文有翻译腔」这类求助明确命中它)。

配套改动:

- `翻译提示词.md` 开工前一段加了「先看一眼本机技能库」, 并声明读不到也能自足执行
  (技能是**增强**, 不是依赖 —— 提示词必须自己站得住)。
- `翻译提示词.md` 第三节新增第 7 条**翻译腔清单** (10 项), 把诊断出的病症写成可执行规则。
  这是纯文本规则, 不依赖技能是否被加载。
- 新增 `docs/翻译腔对照示例.md`: 20 条真实台词的前后对照, 每条标病因。
  既是对照证明, 也是后续润色的范例。
- `使用说明.md` / `CONTEXT.md` 同步说明技能位置与用途。

## 后果

- **技能是方法论, 不是自动流水线**: 仍需把待翻译 JSON 交给对话 agent。
  技能只是让 agent 在翻译时有一份专业作业指导, 不改变工具链的任何环节。
- 提示词里的翻译腔清单与技能内容**有意重叠**: 技能加载失败时提示词仍然完整可用。
  维护时若改动清单, 需与 `docs/翻译腔对照示例.md` 的例证保持一致。
- 手工安装的技能不随客户端更新: 升级/重装后需重新放回 `~/.zcode/skills/`。
  从上游仓库取 tarball 解包放回即可 (本仓库不附带这些技能的源码)。
- 新建的技能**在会话启动时被发现**: 装完要新开一个对话才会出现在 `/` 菜单里。
- 已验证 20 条真实句子的润色稿在变量与标签上零违规 (机器校验),
  平均长度比 0.372 → 0.367 (润色后略短, 符合「中文比英文短」的预期)。
